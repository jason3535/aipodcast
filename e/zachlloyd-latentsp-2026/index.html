本期速览 · Overview

Warp.dev 的 Zach Lloyd 解析软件工厂的真正含义、为何应以代码定义，以及团队构建软件工厂所需的基础设施。

Zach Lloyd of Warp.dev explains what a software factory really is, why it should be defined in code, and what infrastructure teams need to build one.

要点 · TL;DR

  • 软件工厂是可度量、声明式的智能体系统，而非临时拼凑的自动化。
    A software factory is a measurable, declarative agentic system, not ad-hoc automations.
  • 集中管理智能体轨迹，用在线评估以工程严谨性取代感觉。
    Centralize agent traces and use online evals to replace vibes with engineering rigor.
  • 完整技术栈适合 5-10 人以上工程团队；小团队用订阅即可。
    The full stack suits teams of 5-10+ engineers; smaller teams should stick to subscriptions.

核心观点 · Key points

  • 软件工厂是云端智能体系统，具有明确的智能体角色、自主性和闭环度量。
    A software factory is an agentic system in the cloud with defined agent roles, autonomy, and closed-loop measurement.
  • 像Terraform一样用代码声明式定义工厂，以便版本控制、测试并让智能体改进它。
    Define your factory declaratively in code, like Terraform, to version, test, and let agents improve it.
  • 集中所有智能体对话和工件，以实现可观测性、度量和持续调优。
    Centralize all agent conversations and artifacts to enable observability, measurement, and continuous tuning.
  • 在自有运行上使用在线评估和基准测试，用工程严谨性取代感觉。
    Use online evals and benchmarks on your own runs to replace vibes with engineering rigor.
  • 工厂工程是一门新学科：工程师设计构建软件的系统，而不仅仅是软件本身。
    Factory engineering is a new discipline: engineers design the system that builds software, not just software.
  • 这套栈适合5-10人以上的工程团队；更小的团队直接用订阅即可。
    This stack makes sense for teams of 5-10+ engineers; smaller teams should just use subscriptions.

反共识 · Contrarian takes

  • 大多数公司把自动化拼凑起来并不算真正的软件工厂；它必须是一个具体、可度量的系统。
    Most companies stringing together automations don't have a real software factory; it must be a concrete, measurable system.
  • 不要凭感觉追逐新模型和工具链；用基准测试在自有任务上度量它们。
    Don't chase new models and harnesses by vibes; measure them on your own tasks with benchmarks.
  • 对小团队来说，按API付费可能比轮换订阅贵5-50倍。
    Paying API costs can be 5-50x more expensive than rotating subscriptions for small teams.
  • 纯编码智能体业务在经济上不可持续；优化平台避开了这个陷阱。
    Being a pure coding agent business is economically unsustainable; optimization platforms avoid that trap.
  • 自我改进循环可以让智能体针对工厂定义本身发起拉取请求。
    Self-improvement loops can have agents make pull requests against the factory definition itself.
  • 编排器只是栈中的一部分，而不是整个平台。
    The orchestrator is just one piece of the stack, not the whole platform.

在线评估与评分器 Online evals and scorers

Our triage agent was using a really high-powered model. We were doing a bunch of redundant work with the shape of agents — we were doing too many sub-agents relative to just having fewer agents.

Zach

所以我们基本上用这些内置功能做了一堆内部调优和测试，把每个 PR 的成本降到了大概 20 美元或 15 美元，差不多这样。我们能可度量地提升 PR 的吞吐量——过去一个月它涨了 40%。我们测量回滚率，它并没有上升。所以我对“观察、度量、调优”这个总体方法真的很有信心。

And so we basically did a whole bunch of internal tuning and testing using these built-in features, and we were able to get the cost per PR down to like 20 bucks or 15 bucks, something like that. We can measurably improve the throughput of our PRs — over the last month it's gone up by 40%. We measure the revert rate and it hasn't gone up. 编排器与接入点 Orchestrator and access points

Zach

最后，你需要某种编排器。有时候人们把编排器说成是整个平台。我认为它只是其中一块。我说的编排器是指，你需要一个系统，它接收工厂的定义代码，然后真正把工作沿着不同阶段推进，调用正确的模型、加载正确的技能等等。你需要某种能触发正确自动化的东西。

Finally, you need some sort of orchestrator. Sometimes people talk about the orchestrator like it's the whole platform. I think it's a piece of it. What I mean by orchestrator is you need some system that will take the factory definition code and then actually move work along the different stages, calling out to the right models, loading the right skills, etc. You need something that will fire the right automations.

Zach

然后最后，你需要一堆接入点。同样，我们在这方面的理念是——我也能理解别人有不同的理念——我们的理念是把工厂带进公司现有的知识工作工具里。想想最明显的那个：Slack。我们大约 60% 的工作是从 Slack 开始的。但有时候从任务追踪器开始更合理。有时候对一个更习惯在终端里用 Claude Code 的开发者来说，在那里做一堆工作，然后把一份规格提交进工厂，更合理。

And then finally, you need a bunch of access points. And again, our philosophy with this — and I could see people having different philosophies — our philosophy is to bring the factory into a company's existing knowledge work tools. So think of the most obvious one: Slack. We're doing like 60% of our work starting in Slack. But sometimes it makes sense to start in the task tracker. Sometimes it makes sense for a developer who is more comfortable using Claude Code in their terminal to do a bunch of work there and then submit a spec into the factory.

Zach

所以我们的理念是尽量让整个东西由 API 驱动、由 MCP 驱动，让工厂本身成为一块无头基础设施，拥有所有这些不同的入口。所以我觉得这种基于栈的视角——当我展示它、和公司交流时——似乎很能被接受，就是：好，是的，这说得通。这是开发者基础设施栈里的一个新东西。它大致位于 CI/CD 往后一层的位置，但我认为大多数公司都会为软件开发配备类似的东西。

And so our philosophy is to try to make this whole thing API-driven and MCP-driven, so that the factory itself is a piece of headless infrastructure with all these different entry points. So I think this stack-based view of it — when I've shown it and we've talked to companies — seems to land very well, like, okay yes, this makes sense. This is a new thing in the developer infrastructure stack. It kind of sits one level back from where CI/CD is, but I think most companies will have something like this for software development.
